1. Introducción y objetivo

ADO.NET permite ejecutar SQL explícito y mapear manualmente los resultados; Entity Framework Core es un ORM que permite consultar entidades con LINQ y traduce esas expresiones a SQL. La práctica compara ambas alternativas en el mismo módulo TechStore para observar rendimiento, cantidad de código, transacciones y mantenimiento.

El objetivo experimental es comparar operaciones equivalentes sobre SQL Server, con 50,000 productos, 5 categorías, 100 clientes y 1,000 ventas. Las cifras de rendimiento incluidas provienen del CSV generado por las pruebas en esta computadora; no son valores de referencia de internet.

3. Implementación y metodología

ADO.NET

El repositorio usa consultas SQL con parámetros, mapea filas del lector a objetos y ejecuta la venta dentro de SqlTransaction. El ajuste de precios se expresa con un UPDATE SQL; el reporte se calcula con JOIN y GROUP BY.

Entity Framework Core

TechStoreContext configura las entidades, relaciones, restricciones y tipos de columna con Fluent API. Los repositorios usan LINQ y AsNoTracking en consultas de lectura. La migración Inicial define el esquema Code First; el modelo Database First se generó aparte a partir de la base SQL de ADO.NET.

El reporte LINQ se guarda como SQL legible en ConsultaReporteEF.sql. El ajuste masivo se mide cargando entidades y usando ExecuteUpdate.

Procedimiento de medición

Las pruebas se ejecutaron en configuración Release. Cada escenario se repite cinco veces, se descarta la primera ejecución de calentamiento y se promedian las otras cuatro. El temporizador usa Stopwatch y reporta milisegundos.

  • Lecturas de 1,000, 10,000 y 50,000 productos; EF con seguimiento y AsNoTracking.
  • 1,000 búsquedas por Id y 100 búsquedas con texto y categoría.
  • 1,000 inserciones individuales; se eliminan los productos de prueba fuera del tiempo medido.
  • Ajuste de precios, reporte por categoría y 100 ventas de tres productos.

La prueba de ventas restituye el inventario y elimina ventas temporales. Los precios también se restauran a sus valores originales.

Rollback

La opción 5 intentó registrar una venta superior al stock y confirmó que no cambiaron las ventas, los detalles ni el inventario, tanto con ADO.NET como con EF Core.

El estudiante reporta 68 horas de trabajo acumuladas en tres días; el tercer día aún no había terminado. El tiempo corresponde al proyecto completo y no se atribuye artificialmente a cada tecnología.

  1. Dos intentos iniciales del benchmark completo terminaron por timeout SQL. Se optimizó la consulta y se elevó el CommandTimeout a 180 segundos; luego los siete escenarios finalizaron.
  2. La primera ronda mostró latencias de lectura atípicas (66,343 ms para 1,000 productos y 9,573 ms para 10,000). Se repitió el benchmark y se reportan los resultados de la segunda ronda.

Son incidentes de medición observados, no errores inventados de compilación. La compilación Release final reportó 0 errores y 0 advertencias.

6. Análisis y conclusión

En la segunda ejecución, ADO.NET fue más rápido en las lecturas de 1,000 y 10,000 productos (5.82 frente a 11.68 ms con AsNoTracking; 22.24 frente a 24.30 ms), mientras que para 50,000 productos EF Core con AsNoTracking quedó ligeramente por delante (105.50 frente a 116.48 ms). EF con seguimiento fue más lento en esas lecturas, sobre todo al cargar 10,000 o más entidades. Para búsquedas repetidas por ID, ADO.NET tomó 206.61 ms frente a 572.65 ms en EF Core; en las búsquedas filtradas las dos opciones tardaron varios segundos y ADO.NET resultó apenas más rápido.

ADO.NET también fue más rápido al insertar 1,000 productos (550.12 frente a 1,172.33 ms). En cambio, el ajuste masivo con ExecuteUpdate fue el más veloz (15.88 ms), comparado con 96.46 ms en ADO.NET y 446.64 ms cargando y guardando entidades. El reporte agregado tardó casi lo mismo en ambos enfoques, y EF Core fue más rápido en la prueba de 100 ventas (286.89 frente a 336.08 ms). El repositorio ADO.NET contiene 293 líneas frente a 163 en EF Core; el ORM reduce código repetitivo, aunque eso no implica que gane en todos los tiempos.

La conclusión es que no hay un ganador universal: el resultado depende de la operación, del seguimiento de entidades, del SQL generado y del entorno. Además, la primera ronda tuvo tiempos de lectura extraordinariamente altos (66,343 ms para 1,000 filas y 9,573 ms para 10,000), frente a 5.82 y 22.24 ms en la segunda ronda. Esta variación limita la precisión de comparar una sola ejecución; se deben repetir las pruebas bajo condiciones controladas antes de generalizar.

Recomendación para TechStore

Recomiendo EF Core como opción principal para el CRUD y las consultas de negocio por su menor cantidad de código, mapeo y mantenimiento más directo. Para lecturas masivas usaría AsNoTracking; para actualizaciones masivas, ExecuteUpdate, que fue la variante más rápida en esta medición. Mantendría ADO.NET para operaciones de alta frecuencia o consultas que requieran control explícito del SQL, pero solo cuando benchmarks repetidos demuestren una ventaja relevante. La elección final debe considerar también mantenibilidad, transacciones y requisitos del equipo, no solo estos tiempos locales.

Enfoque Model First

EF Core no incluye el diseñador visual de Model First basado en .edmx. Ese enfoque pertenece a EF6 para proyectos de .NET Framework. Code First y Database First son los enfoques comparados en este proyecto; Model First con EF6 es un bonus opcional de la práctica.
